# Topic Work Phase Workflow Design

## Goal

Redesign Research OS so Atlas, Frontier, and Divergent research happen inside one topic work page instead of creating visible child research sessions. Each phase can run independently, can continue from prior phase artifacts, and can accept user edits to AI-generated outputs before those outputs become inputs to the next phase.

## Product Model

The user-facing model changes from "runs chained together" to "one work page with multiple research phases."

- Work: the user-visible research workspace for one topic.
- Phase: Atlas, Frontier, or Divergent inside the work.
- Phase execution: one run of one phase, including status, events, budget, inputs, and output bundle.
- Artifact card: a structured, editable output generated by a phase.
- Selection: the set of artifact cards chosen as input for a later phase.

The existing `research_run` table can remain as the short-term execution primitive, but the user should not see labels such as `[divergent] child of Frontier Run` as separate research items. A run is implementation detail. The stable user surface is the topic work page.

## Requirements

- Keep Atlas, Frontier, and Divergent visible in one topic work page.
- Do not create visible child research sessions for normal phase progression.
- Let every phase run independently from manual inputs.
- Let every phase run from selected and edited upstream artifact cards.
- Give every phase a clear "next phase" action:
  - Atlas -> Frontier from selected direction/taxonomy cards.
  - Frontier -> Divergent from selected gap and pain-point cards.
  - Divergent -> Frontier validation from selected idea cards, still inside the same work.
- Convert phase outputs from report-only surfaces into editable structured cards.
- Track artifact provenance: generated phase, source execution, user edits, selection state, and downstream usage.
- Preserve current mode-specific agents and worker graphs where possible.
- Preserve existing run event streams for execution observability.
- Avoid destructive migration of existing research data.

## Non-Goals

- Full collaborative editing.
- Fine-grained text diff UI for every card field.
- Removing `research_run` immediately.
- Rewriting Atlas, Frontier, or Divergent worker graphs from scratch.
- Building a visual canvas. The first version remains a structured operational UI.

## Interaction Design

The work page uses a three-phase stepper or tabs:

```text
Atlas -> Frontier -> Divergent
```

Each phase tab contains:

1. Phase status and latest execution summary.
2. Input deck: manual inputs plus selected upstream artifact cards.
3. Editable artifact cards generated by the phase.
4. Phase run history for prior executions of that phase.
5. Primary actions for running this phase or continuing to the next phase.

### Atlas Phase

Atlas can start from topic, keywords, seed papers, and library pools. It produces cards such as research directions, taxonomy nodes, representative papers, foundational concepts, and reading-path units.

Primary actions:

- `Run Atlas`
- `Start Frontier from selected Atlas cards`

If no Atlas cards are selected, Frontier can still run independently from manual Frontier inputs.

### Frontier Phase

Frontier can start from manual sub-field scope inputs or selected Atlas cards. It produces cards such as gaps, pain points, method landscape entries, benchmark entries, entry points, and paper review summaries.

Primary actions:

- `Run Frontier`
- `Start Divergent from selected gaps`

If no Frontier cards are selected, Divergent can still run from manually entered pain points or innovation prompts.

### Divergent Phase

Divergent can start from manual pain points or selected Frontier gap/pain cards. It produces idea cards, prior-art risk cards, feasibility cards, and recommended next-step cards.

Primary actions:

- `Run Divergent`
- `Validate selected ideas with Frontier`

Validation is a Frontier execution inside the same work. It should appear under the Frontier phase as a validation execution, not as a visible child session.

## Editable Artifact Cards

Cards are the handoff contract between phases. Every card has:

- `id`
- `work_id`
- `phase`
- `artifact_type`
- `title`
- `body`
- `payload`
- `status`
- `selection_state`
- `source_execution_id`
- `source_card_ids`
- `created_by`
- `updated_by`
- `created_at`
- `updated_at`

The UI supports:

- Edit card title and structured fields.
- Delete or archive a card.
- Select or deselect a card for a downstream phase.
- Show whether a card is AI-generated, user-edited, or used by a downstream phase.
- Open provenance for a card: which execution created it and which execution consumed it.

Cards should use a generic storage model plus typed UI adapters. For example, a `frontier_gap` card can store common display fields in `title` and `body`, with detailed structured data in `payload`.

## Data Model Direction

Introduce a new work-level layer while keeping `research_run` as the execution backend:

- `research_work`: one topic workspace visible in the sidebar.
- `phase_execution`: one execution of Atlas, Frontier, Divergent, or Frontier validation inside a work.
- `artifact_card`: editable structured card output.
- `artifact_revision`: append-only revision history for user and AI edits.
- `phase_input_selection`: selected cards and manual inputs for a phase execution.

Short-term compatibility:

- Existing root `research_run` rows can be treated as works during migration.
- Existing mode-specific pages can be folded into `/works/[id]` or adapted behind `/runs/[id]` until routing migration is complete.
- Existing `idea_card` can remain for Divergent-specific persistence while `artifact_card` becomes the cross-phase user-facing abstraction.

## API Design

Add work-centered endpoints:

- `POST /api/v1/works`
- `GET /api/v1/works`
- `GET /api/v1/works/{work_id}`
- `GET /api/v1/works/{work_id}/phases`
- `POST /api/v1/works/{work_id}/phases/{phase}/executions`
- `GET /api/v1/works/{work_id}/artifact-cards`
- `POST /api/v1/works/{work_id}/artifact-cards`
- `PATCH /api/v1/works/{work_id}/artifact-cards/{card_id}`
- `POST /api/v1/works/{work_id}/phase-inputs/{phase}`

The phase execution endpoint builds a queue payload from:

- manual inputs saved for the target phase.
- selected upstream artifact cards.
- work-level topic, keywords, seed papers, library pools, budget, and policy.

## Worker Data Flow

1. User edits and selects artifact cards in the work page.
2. User starts a target phase.
3. API creates a `phase_execution` row and either creates or reuses a backing `research_run` row.
4. API flattens selected cards into the `context_bundle` shape expected by the target worker graph.
5. Worker runs the existing Atlas, Frontier, or Divergent graph.
6. Persistence writes existing mode outputs as today.
7. A card extraction layer converts output bundles into `artifact_card` rows.
8. Work page refreshes phase status, cards, and execution history.

## UI Structure

Main work page:

- Header: topic, work status, last updated, quick run controls.
- Phase stepper: Atlas, Frontier, Divergent.
- Active phase panel:
  - input deck
  - editable cards
  - execution activity
  - next-phase action
- Context drawer:
  - selected directions
  - selected gaps
  - selected ideas
  - seed papers
  - library papers

Sidebar:

- Show works, not child runs.
- Secondary metadata should show phase progress, for example `Atlas done, Frontier running`.
- Do not expose `child of` labels.

## Error Handling

- Starting a phase without upstream cards is allowed if manual inputs are present.
- Starting a phase with neither upstream cards nor meaningful manual input returns a validation error.
- Editing a card already used by a downstream execution creates a new revision and marks downstream usage as based on an older revision.
- If phase execution enqueue fails, phase status returns to its previous state and the work page shows a concise error.
- If card extraction fails after a worker completes, the raw output bundle remains accessible and the phase shows a recoverable extraction error.

## Migration Strategy

Use an additive migration:

1. Add new tables without removing existing columns.
2. Backfill one `research_work` per root `research_run`.
3. Backfill one `phase_execution` for each existing run.
4. Backfill cards from existing `context_bundle`, `pain_point`, and `idea_card` rows where possible.
5. Keep old `/runs/{id}` routes during transition.
6. Move sidebar and new research flows to works after API coverage is in place.

## Testing Strategy

- Database tests for new table inserts, updates, revision history, and work access scoping.
- API tests for work creation, phase execution enqueue, card CRUD, and selection payload shaping.
- Worker/persistence tests for output bundle to artifact card extraction.
- Static UI tests for single-work navigation, phase CTAs, and absence of visible child-session text.
- Build verification with `npm --prefix apps/web run build`.

## Open Decisions

- Whether to route new pages under `/works/[id]` immediately or keep `/runs/[id]` as a compatibility alias.
- Whether every phase execution should have its own backing `research_run` row or whether the existing root run should be reused for multiple executions.
- Whether card editing should be inline only in the first version or allow a full-screen editor for complex cards.
